## 3. Prioritized baseline findings

Priorities describe this product's timing-integrity, availability, privacy, and release risks. They are not CVSS scores or claims of remotely exploitable code execution. **R1** means resolve or explicitly constrain the affected product/release claim before public release. **R2** means complete hardening and evidence before broad distribution. A valid-looking poisoned HTTPS response requires control of the source or a device-trusted intermediary; an ordinary network attacker can instead exploit failure/delay behavior without forging certificates.

| --- | --- | --- | --- |

No freshness expiry is applied. **Observed source behavior; runtime not tested.** | After one success, network blocking or any later failure leaves an old anchor while a render tick hides the failure. A user can mistake an indefinitely extrapolated value for a successful sync. | SEC-03: persistent quality/error state independent of rendering; monotonic last-accepted age; failure and expiry cases T-09, T-10. |

## 4. How to conduct the next review

Start by freezing scope: record commit and working-tree diff, source hashes, expected endpoint and timestamp meaning, supported macOS/architectures, distribution channel, and the proposed numerical limits selected from the guidelines. Enumerate callers that can initiate sync and all code that can mutate the anchor, accepted age, quality state, timers, and session. Trace a success, failure, rejected redirect, hide/show, and shutdown from input to UI. This prevents a fix to one button from leaving another path unprotected.

Next review trust boundaries and state transitions together. For every external field or asynchronous callback, ask what authority it carries, what validation occurs, and whether rejection can nevertheless update an anchor, success age, or visible status. Treat attacker-controlled sequences as first-class inputs: repeat, reorder, delay, overlap, downgrade, and resume. This adapts OWASP's data-flow threat modeling and business-logic timing/workflow testing to a native client; it is not a claim that the whole web testing standard applies. [OWASP: Threat Modeling](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html), [OWASP WSTG v4.2: Business Logic Testing](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/10-Business_Logic_Testing/)

Then execute the approved cases in a controlled environment. Use deterministic response fixtures, a controllable elapsed clock, and a local test server where real transport behavior matters. Keep traffic away from Tixcraft for malformed-input, replay, race, and stress scenarios. Test TLS failures without adding exceptions to production code or weakening the everyday machine's trust store; use a disposable environment for certificate tests. Do not run the existing browser probe as a prerequisite. Implementing a harness or modifying code belongs to a later implementation task.

Finally inspect the exact release candidate and its chain to source. Record results and close findings only when the relevant invariant is proven at the appropriate layer. Static parser tests cannot establish URLSession behavior, sleep behavior, actual entitlements, or distribution trust. Feed root causes and repeatable evidence into subsequent releases; this lightweight process is consistent with the secure-development approach described by NIST SSDF, without implying certification. [NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final)

## 5. Adversarial verification matrix — all planned, not run

Expected results below refer to the proposed design. Values such as cooldown and expiry come from the approved policy for the future implementation. Test both the unsafe input's rejection and the absence of side effects: unchanged accepted anchor/age, correct visible state, terminated work, and bounded traffic.

| Case / requirement | Controlled stimulus | Required result and evidence |
| --- | --- | --- |
| T-01 / SEC-01 | Local HTTPS fixtures with invalid chain, expired certificate, wrong hostname, and HTTP downgrade; offline/DNS-failure variants | Connection fails under platform trust; no insecure retry, accepted sample, or false recent state. Capture request destinations and state outcome. |
| T-02 / SEC-01 | Redirect to off-host, HTTP, same-host non-443 port, alternate path, userinfo URL, and loop; include a plausible Date on the original 3xx | Proposed no-redirect policy follows none and accepts no original timestamp. Test the delegate/final-response path, not just a URL helper. |
| T-03 / SEC-01/02 | Identical plausible time headers on 200, 204, 301/302, 304, 401, 403, 429, and 500/503; valid, malformed, and long Retry-After | Only eligible 2xx candidates progress to time validation. Other responses preserve rejection/degradation and appropriate backoff. Document the intentional change from the old 403 self-test. |
| T-04 / SEC-02 | Valid grammar controls plus NaN, infinity, overflow, exponent/sign variants outside approved grammar, duplicate S fields, invalid leap dates/timezones, trailing text, and oversized fields | Reject invalid/ambiguous input promptly without crash or anchor mutation; Date parsing consumes the approved format; memory and runtime remain bounded. |
| T-05 / SEC-02/03 | Valid but old values within 2000–2100; aged cache response; repeated Date; absent/zero Age; contradictory Date and X-Timer | Cache metadata never proves freshness by itself. Stale/inconsistent observations cannot refresh confidence; first-launch limitations remain visible. |
| T-06 / SEC-02 | Single rollback/forward jump followed by many individually small shifts; repeat after hide/show and settings changes | Check both discontinuity and cumulative drift; quarantine suspicious values and do not reset the detection history through a UI shortcut. A consistently false source is documented as an unresolved authority limit. |
| T-07 / SEC-02 | Fractional X-Timer sequence that increases within one second; Date-only second transitions; missing X-Timer then valid/invalid/conflicting X-Timer | Source semantics remain distinct. No fractional increase is treated as proof of a Date boundary. Fallback cannot increase confidence or erase the reason for degradation. |
| T-08 / SEC-02/03 | Fixture timestamps with known outbound delay, inbound delay, and server processing; vary each independently while keeping others fixed | Measure estimator error against fixture truth; high delay/asymmetry reduces confidence or rejects the sample. Do not assert RTT/2 or displayed hundredths as a guaranteed accuracy bound. |
| T-09 / SEC-03 | One accepted sample, then timeout/rejection, then many display refreshes and manual Sync calls | Error/degraded state persists until actual acceptance; old anchor age is not reset; stale threshold is applied while display continues. This is the direct regression for F-01. |
| T-10 / SEC-03/05 | Move local wall time forward/backward and across date boundaries; change timezone while observations age | UTC anchor progression, cooldown, and expiry use correct elapsed-time semantics; no negative age, false recent state, or unsafe numeric conversion. Taipei display remains intentional. |
| T-11 / SEC-04 | Rapid Sync button/menu events, reopen/show events, and timer ticks before and after each completion | All paths share concurrency, cooldown, per-attempt count, and rolling budget; no duplicate work or burst after completion. Capture counts across the full sequence. |
| T-12 / SEC-04 | Fast identical timestamps, slow incremental response data, request completion after nominal deadline, repeated service errors | Absolute attempt deadline and count limits terminate work; idle timeout is not the only bound; failure backoff is shared and preserves staleness. |
| T-13 / SEC-04 | Response callback before/after metrics, absent or failed diagnostics, cancellation at each stage | Exactly one terminal outcome, synchronization slot released, no dependence on diagnostics for correctness, no deadlock. This tests a hypothesis, not a previously reproduced hang. |
| T-14 / SEC-04/05 | Deliver completion/metrics from an old attempt after a newer attempt exists; cancel immediately before committing an anchor | Obsolete callbacks cannot mutate anchor, accepted age, metrics association, or quality state. Record attempted and accepted generation transitions. |
| T-15 / SEC-05 | Hide via app menu and clock menu during collection; trigger hidden Sync; show repeatedly | Under the proposed policy, hide cancels pending collection and scheduled work; no new hidden requests; show reacquires subject to the same budget. |
| T-16 / SEC-03/05 | Sleep longer than expiry during idle and in-flight states; wake without network, then restore it | No pre-sleep sample is presented as recent; obsolete work cannot commit; elapsed-time semantics and recovery are correct on each supported OS/architecture. |
| T-17 / SEC-04/05 | Close/Quit during requests, retry delay, metrics collection, and queued UI updates | No surviving app-owned network work or timers, no callback mutation after shutdown, and clean process exit. Test actual lifecycle integration, not only the shutdown helper. |
| T-18 / SEC-06 | Local server sets a cookie and requests credentials; restart app and inspect the sandbox container and request headers | No automatic cookies, authorization, or credential persistence for the clock feature; no raw headers or identifiers leaked to logs. Ephemeral alone is not sufficient evidence. |
| T-19 / SEC-06 | In a disposable app profile, set missing, wrong-type, nonfinite where representable, huge, negative, and unsupported interval values | Safe approved default before conversion/timer creation; no crash, busy timer, or indefinitely disabled synchronization. No claim of remote exploitability. |
| T-20 / SEC-04/06 | Unsolicited HEAD response content, oversized response metadata, long errors, and many failed attempts on a local fixture | No unbounded buffering, diagnostic accumulation, thread growth, or UI freeze; task cancellation and storage limits are observable. |
| T-21 / SEC-06/08 | Developer-only probe: occupied debugger port, failed Chrome launch, unresponsive CDP call, lingering process, unusual target argument | Fail without attaching to another process or personal profile; bounded wait and owned-resource cleanup; debugger exposure verified as loopback-only. Do not ship probe artifacts. |
| T-22 / SEC-07 | Inspect a clean release build and both slices: signature identity, hardened flags, entitlements, metadata, libraries, resource list, and version | Reviewed least-privilege bundle, expected team identity and timestamp, no debug exceptions, no extra developer tools, and provenance to the recorded source. |
| T-23 / SEC-07 | Verify exact final app/DMG, notarization and stapled-ticket evidence, clean-machine Gatekeeper behavior; alter a copy after signing | Intended artifact passes applicable distribution checks; modified copy fails integrity verification. Record hashes and signer, not just a generic pass message. |
| T-24 / SEC-07/08 | Compare an older known artifact and current candidate; rehearse release credential isolation and a tampered-artifact incident without publishing | Clear version/provenance distinction and documented recovery owner; untrusted contributions cannot access release secrets. No automatic-update rollback test is required while no updater exists. |
| T-25 / SEC-08 | Repeated failures and transitions with local diagnostics enabled in a future implementation, then explicit user export | Useful bounded rejection/state evidence, no sensitive raw data, predictable retention, and no unsolicited upload. |

For transport fixtures, measure actual requests, not just calls to a mock. For estimator fixtures, control observation time independently of wall time. For UI tests, assert the visible meaning after repeated refreshes, not a single callback's status string. Use tests that enforce these invariants rather than reproducing the implementation's current branching.

## 7. Finding records and release decisions

Record each finding with ID, reviewed revision/hash, exact location, evidence label, attacker prerequisites, violated SEC property, user-visible consequence, smallest controlled reproduction, proposed correction, owner, priority, and closure evidence. A risk acceptance must name the residual behavior and affected release claim, its owner and review date; it must not convert a missing test into a pass.

Before public distribution, close the R1 findings relevant to the intended behavior and establish artifact authenticity. Complete R2 checks before broad distribution or document a bounded exception with a concrete follow-up. Recheck changed boundaries on each PR; rerun the applicable security matrix and final artifact checks on releases. Trigger a full model update for new network sources, permissions, persistence, IPC, telemetry, updater, account, backend, or ticketing automation capability.

The present conclusion is limited but actionable: the project already narrows its runtime surface and retains useful native protections, while time integrity, persistent error/freshness state, request/lifecycle bounds, and public-release provenance need explicit design and verification. No runtime security fix, exploit, live-service assessment, or public-release approval was performed here.
